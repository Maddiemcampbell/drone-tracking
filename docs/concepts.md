# Concepts

- **Ground truth** is the actual simulated state, used for drawing and evaluation, never by a tracker.
- **Measurement noise** is random sensor error; x and y currently use independent Gaussian noise.
- **Measurement covariance** describes uncertainty; diagonal entries contain the x/y noise variance.
- **Sensor update rate** is the interval between measurements, independent of the integration timestep.
- **State estimation** would infer position and velocity from imperfect observations. This view labels observations explicitly and does not turn noisy dots into a tracker estimate.
- **Heading** is the direction of travel measured counterclockwise from positive x. Configuration uses degrees; motion math uses radians.
- **Standard deviation vs. variance**: σ describes the typical measurement error in meters; covariance stores σ² in its diagonal. x and y noise are independent.
- **Sampling schedule**: measurements occur at `k × interval` for integer k, including t=0 and any schedule time through the run duration. A sample is not snapped to the nearest simulation tick.
- **Radar-style measurement**: the simplified range/bearing sensor measures distance in meters and bearing relative to the sensor heading. Bearing is configured in degrees but stored in radians; its covariance entry is therefore in rad², while range covariance is in m².
- **Radar edge cases**: a target at the sensor origin has no defined bearing, so that observation is omitted. A negative noisy range is invalid and omitted rather than clamped. No field-of-view or detection-range logic is included.
- **Radar visualization**: the UI converts a valid range/bearing pair back to world x/y for display. That conversion is not a new Cartesian observation; the range/bearing pair is authoritative. Cartesian errors derived from it can be correlated and distance-dependent.
- **Coordinate frames**: radar bearing is sensor-local. The UI adds the sensor’s world heading, then converts range and bearing into the shared world Cartesian frame before drawing or evaluating position error.
- **Noise illustration**: the optional overlay shows configured x/y spread for Cartesian measurements, or range circles and bearing rays for radar. These are teaching aids for the configured standard deviations, not guaranteed bounds or confidence regions.
- **Sensor mode**: the selector chooses Cartesian mode (which can emit two independent position streams) or radar-style mode (sensor-only). Multi-sensor fusion remains intentionally deferred.
- **Two Cartesian sensors**: the position sensor and simplified camera sensor can each be enabled independently. Both observe the same world-frame truth, but each has its own ID, x/y standard deviations, constant bias, sampling interval/start offset, outages, and deterministic random stream. The first sensor milestone emits both streams; asynchronous fusion is a later step.
- **Simplified camera model**: the camera reports world-frame x/y directly. It does not process images or model optics, depth, occlusion, or calibration. Real camera position estimates need additional geometry and calibration.
- **Per-sensor schedules**: sensor samples occur at `start_offset + k × interval` using an integer sample index. Different sensors are not resampled to a common frequency. Simultaneous observations are emitted in deterministic sensor-ID order.
- **Independent sensor randomness**: each sensor owns a reproducible seeded Gaussian stream. Outage samples are omitted after consuming only that sensor's draw, so changing or disabling one sensor does not change another sensor's measurements.
- **Simulator-only evaluation**: position error metrics can compare observations with truth at the measurement timestamp because this simulator retains truth. A deployed sensor would not provide that truth reference.
- **Causal Kalman tracker**: the Cartesian tracker starts with measured position, zero velocity, and configured velocity uncertainty, then predicts with a constant-velocity transition and continuous white acceleration noise. It updates with each available Cartesian measurement at its timestamp; early velocity estimates still need several observations to settle.
- **Tracker covariance**: the tracker uses state ordering `[x, y, vx, vy]` and a 4×4 covariance. Its acceleration noise spectral density `q` has units m²/s³. Prediction uncertainty grows with positive `q` and elapsed time.
- **Radar and tracking**: radar range/bearing remains sensor-only in this milestone. The tracker accepts Cartesian x/y observations only; it does not consume radar values or truth.
- **Causal timing**: measurement and output events are merged chronologically. A measurement at an output timestamp is applied first, and future observations cannot change earlier estimates. Delayed measurements are rejected until a later delay-aware milestone.
- **Sensor outages**: an outage omits scheduled observations in the half-open interval `[start, end)`, while true motion and the measurement schedule continue. Prediction remains active, the last measurement timestamp is preserved, and measurement age reports how long the track has gone without a reading.
- **Unseen turns**: the filter assumes approximately constant velocity. It cannot know that a turn happened while measurements were missing; process noise captures motion-model uncertainty, so prediction can continue while accuracy deteriorates.
- **Prediction**: advances the state and covariance through elapsed simulation time using the constant-velocity model. During an outage it continues without inventing a measurement, while measurement age records how long the track has gone without an update.
- **Update**: incorporates a newly available Cartesian observation through the Kalman innovation. An estimate marked “updated” used a measurement at that output timestamp; otherwise it is prediction-only.
- **Process noise**: `q` is acceleration-noise spectral density in m²/s³. Lower `q` favors smooth, less responsive estimates; higher `q` allows more motion variation. This motion-model uncertainty is different from measurement uncertainty.
- **Position uncertainty ellipse**: the UI uses the estimate's x/y covariance block and chi-square factor 5.991 for a 95% model ellipse. It is not a guaranteed boundary or a tracker confidence region independent of the filter assumptions. A biased sensor can therefore produce a confidently wrong estimate.
- **Tracking evaluation**: tracker RMSE and a held-measurement baseline are compared at the same emitted output timestamps after an optional warm-up. This is possible only because the simulator retains truth; truth is not tracker input.
- **Remaining tracking milestones**: nonlinear radar tracking, delayed observations, sensor fusion, and multi-target data association remain intentionally out of scope.
